## Outcome

Move 3 of 3, closing #49, #50, #51, #55 and #29 in one branch. `mc_draft()` and `mc_md_draft()` now return `list(draft_id, thread_id, message_id)`, and `draft_id =` replaces exactly that draft through Gmail's `drafts.update` (gmailr 3.0.0 has no update call, so mc sends the JSON draft resource itself, as `gmail_modify_thread()` already did for labels). An id Gmail does not know warns and creates a new draft; mc never deletes one. `mc_md_draft()` records the id in the file's frontmatter (`frontmatter_set()`: one line, the rest byte for byte, read back before it replaces the file), so re-running a file replaces its own draft. Drafts with `thread_id` are created in the thread, and drafts and sends into a thread carry `In-Reply-To`/`References` (validated msg-ids only) and a `Re: ` subject. `mc_thread_read()` and `mc_message_find()` classify drafts by the `DRAFT` label, and draft searches carry the query. What was learned: the plan review and three code-check rounds each found real defects, and two classes recurred. The first was a check and an action resolving different objects: a `to_self` guard read before `override` applied, `$` partial-matching `draft_id_old:` and `cc_old:` (the latter a pre-existing send risk, fixed with all 30 frontmatter reads), and a rename over a symlink. The second was the write position inside YAML: a key appended after a trailing block scalar. Round 3 named the mechanism and enumerated 26 places; the loop ended on that enumeration. The gate's note that a `to_self` run records its id was corrected after the plan review: a `to_self` draft is a separate test copy and leaves the tracked draft alone.

## Measurement

Live Gmail, `MC_RUN_INTEGRATION=true`, 2026-11-05 23:51Z: 67 integration tests pass. An 8 MB random attachment survives create and then `PUT drafts/{id}` through the non-upload JSON endpoint (the replaced draft's attachment part > 7.9e6 bytes), so the multipart-upload fallback the review proposed was not needed at that size. A `PUT` with `threadId` keeps a draft in its thread; one without moved it to a new thread. A label given again on replace stays; a replace without `labels` dropped it. A message id passed as a draft id gets the same 404 as a deleted draft. These turned four assumptions into documented behaviour on `mc_draft()`. Unit suite: 615 pass after Phase 1, 715 at the end, 0 failed; lints unchanged from main apart from 2 fewer in `test-mc_thread_read.R`.
